# SWITCH KOREA 영업망 관리 모듈 설계

**작성일:** 2026-10-06  
**대상 시스템:** SWITCH KOREA 영업관리 시스템  
**모듈:** 2. 영업망(네트워크 및 계보도)

## 1. 목적

기존 거래처와 잠재 협력사를 하나의 영업망에서 관리하고, 삼성전자·LG전자 등 원청을 기준으로 다단계 협력사 관계를 조회한다. 거래처 외부 담당자와 당사 영업담당자 변경 이력을 함께 보존하여 담당자 변경 후에도 영업 관계와 인수인계 정보를 추적할 수 있게 한다.

성공 기준은 다음과 같다.

- 한 회사가 여러 원청의 공급망에 동시에 연결된다.
- 공급망의 계층 깊이에 제한을 두지 않는다.
- 아직 거래하지 않는 잠재 협력사를 등록하고 이후 정식 거래처로 전환할 수 있다.
- 회사 간 관계에 납품 품목, 적용 제품·프로젝트와 거래 기간을 기록한다.
- 거래처 담당자와 당사 담당자의 현재 정보 및 과거 이력을 조회한다.
- 기존 영업관리 모듈의 사용자·거래처·품목·권한·감사 체계를 재사용한다.

## 2. 범위

### 2.1 포함

- 영업망 회사 등록, 조회, 수정 및 사용 중지
- 기존 거래처와 영업망 회사의 1:1 연결
- 잠재 협력사의 정식 거래처 전환
- 원청·협력사 간 다중 연결과 무제한 계층 조회
- 관계별 거래 기간, 납품 품목, 적용 제품·프로젝트 및 비고
- 거래처 외부 담당자 복수 등록과 재직·담당 기간 이력
- 당사 영업담당자의 현재 배정 및 변경 이력
- 담당자별 수정 권한과 팀장 전체 관리 권한
- 관계·연락처·담당자 변경 감사 기록

### 2.2 제외

- 외부 기업정보 서비스 자동 수집
- 글로벌 잠재고객 자동 리서치
- 견적서와 고객문의 처리
- 이메일·문자 자동 발송
- 그래프 전용 데이터베이스 도입
- 영업망 데이터 Excel 일괄 등록
- 네트워크 중심성 등 고급 관계 분석

제외 항목은 후속 모듈 또는 별도 개선 과제로 다룬다.

## 3. 설계 원칙

1. 기존 거래처 데이터를 중복 생성하지 않고 영업망 회사와 연결한다.
2. 회사와 회사 간 관계를 별도 데이터로 관리하여 다중 원청 연결을 지원한다.
3. 협력사 단계는 저장하지 않고 선택한 원청에서의 경로를 기준으로 계산한다.
4. 실제 삭제보다 사용 중지와 유효기간을 사용하여 과거 이력을 보존한다.
5. 현재 담당자 조회와 담당자 이력을 분리하지 않고 동일 화면에서 제공한다.
6. React/TypeScript, ASP.NET Core Web API, PostgreSQL의 기존 구조를 유지한다.

## 4. 사용자와 권한

### 4.1 공통 조회

로그인한 사용자는 전체 영업망, 회사 관계, 납품정보 및 거래처 담당자를 조회할 수 있다.

### 4.2 팀원

- 본인이 담당하는 영업망 회사의 기본정보와 외부 담당자를 수정한다.
- 본인 담당 회사가 상위 또는 하위 회사로 포함된 관계를 등록·수정한다.
- 잠재 협력사를 등록하면 등록자가 현재 당사 담당자가 된다.
- 다른 담당자의 회사와 당사 담당 이력은 조회만 가능하다.

### 4.3 팀장

- 모든 영업망 데이터를 등록·수정·사용 중지한다.
- 잠재 협력사를 정식 거래처로 전환한다.
- 회사의 당사 담당자를 변경한다.
- 충돌하거나 잘못 연결된 관계를 정리한다.

## 5. 화면 구조

기존 왼쪽 메뉴에 `영업망 관리`를 추가한다. 기본 화면은 승인된 `계층 탐색 + 상세 패널` 구조를 사용한다.

### 5.1 상단 검색 영역

- 원청 선택
- 회사 구분: 전체, 원청, 정식 거래처, 잠재 협력사
- 당사 담당자 선택
- 회사명 검색
- 사용/중지 상태
- 회사 등록 버튼

### 5.2 왼쪽 계보도

- 선택한 원청부터 하위 협력사를 단계별로 펼치거나 접는다.
- 동일 회사가 여러 원청에 연결되면 각 원청 계보에 표시한다.
- 정식 거래처와 잠재 협력사를 배지로 구분한다.
- 회사를 선택하면 오른쪽 상세 패널을 갱신한다.
- `관계 연결` 기능으로 상위·하위 회사를 연결한다.

### 5.3 오른쪽 상세 패널

다음 탭을 제공한다.

1. **기본정보:** 회사명, 국가, 업종, 구분, 상태, 현재 당사 담당자
2. **관계·납품:** 상위·하위 회사, 거래 기간, 등록 품목, 적용 제품·프로젝트, 비고
3. **거래처 담당자:** 성명, 부서, 직위, 업무 역할, 휴대폰, 이메일, 담당 기간, 재직 상태
4. **당사 담당 이력:** 담당 직원, 시작일, 종료일, 현재 담당 여부
5. **변경 이력:** 수행자, 시각, 대상, 작업, 변경 전·후 값

## 6. 데이터 개념 모델

### 6.1 NetworkCompany

영업망에 표시되는 모든 회사를 나타낸다.

- `Id`
- `CompanyName`
- `Country`
- `Industry`
- `LifecycleType`: Customer, Prospect
- `IsOem`: 원청 여부
- `CustomerId`: 기존 거래처 연결, 잠재 협력사는 null
- `Status`: Active, Inactive
- `Version`: 낙관적 동시성

`CustomerId`는 1:1 고유 연결이다. 기존 거래처에는 마이그레이션 시 대응하는 영업망 회사를 생성한다.

### 6.2 CompanyRelationship

회사 간 방향성 있는 공급 관계를 나타낸다.

- `Id`
- `UpstreamCompanyId`
- `DownstreamCompanyId`
- `ValidFrom`
- `ValidTo`
- `Notes`
- `Status`
- `Version`

활성 기간이 겹치는 동일 상위·하위 관계의 중복 등록을 차단한다. 자기 자신과의 연결과 순환 관계도 차단한다.

### 6.3 RelationshipSupply

회사 관계별 납품 내용을 나타낸다.

- `Id`
- `RelationshipId`
- `ProductId`: 기존 품목 마스터 연결
- `ApplicationName`: 적용 제품 또는 프로젝트
- `Notes`

한 관계에 여러 품목을 연결할 수 있다.

### 6.4 CompanyContact

거래처 외부 담당자를 나타낸다.

- `Id`
- `CompanyId`
- `Name`
- `Department`
- `Position`
- `BusinessRole`
- `MobilePhone`
- `Email`
- `ValidFrom`
- `ValidTo`
- `EmploymentStatus`: Active, Former
- `Version`

담당자가 변경되거나 퇴사해도 기존 행을 삭제하지 않는다.

### 6.5 CompanyAssignment

당사 영업담당자 배정 이력을 나타낸다.

- `Id`
- `CompanyId`
- `UserId`
- `ValidFrom`
- `ValidTo`
- `IsCurrent`
- `Version`

회사마다 현재 주 담당자는 한 명만 허용한다. 담당자 변경은 기존 현재 배정의 종료일을 기록하고 신규 배정을 생성하는 하나의 작업으로 처리한다.

## 7. 주요 업무 흐름

### 7.1 잠재 협력사 등록

1. 팀원이 회사 기본정보를 입력한다.
2. 회사 생애주기 구분을 `Prospect`로 저장한다.
3. 등록한 팀원을 현재 당사 담당자로 배정한다.
4. 감사 이력을 기록한다.

### 7.2 공급망 관계 등록

1. 사용자가 상위 회사와 하위 회사를 선택한다.
2. 시스템이 자기 연결, 중복 및 순환 여부를 검사한다.
3. 거래 기간과 납품 품목·적용 프로젝트를 입력한다.
4. 권한 확인 후 관계와 납품정보를 저장한다.
5. 계보도를 다시 계산하여 표시한다.

### 7.3 잠재 협력사 전환

1. 팀장이 잠재 협력사에서 `정식 거래처 전환`을 선택한다.
2. 거래처 코드, 기본 통화 등 거래처 필수정보를 입력한다.
3. 거래처를 생성하고 영업망 회사의 `CustomerId`를 연결한다.
4. 기존 회사 관계·연락처·담당 이력은 유지한다.
5. 전체 작업을 하나의 트랜잭션과 감사 이력으로 기록한다.

### 7.4 당사 담당자 변경

1. 팀장이 신규 담당자와 변경 적용일을 선택한다.
2. 기존 현재 배정의 종료일을 적용일 전날로 기록한다.
3. 신규 배정을 생성하고 현재 담당자로 지정한다.
4. 기존 거래처의 현재 담당자 정보도 동일하게 갱신한다.
5. 변경 전·후 내용을 감사 이력에 기록한다.

## 8. API 경계

영업망 기능은 기존 `/api` 인증 및 권한 체계를 사용한다.

- `/api/network/companies`: 회사 조회·등록·수정·사용 중지
- `/api/network/companies/{id}/convert`: 잠재회사 거래처 전환
- `/api/network/relationships`: 관계 조회·등록·수정·사용 중지
- `/api/network/companies/{id}/contacts`: 외부 담당자 관리
- `/api/network/companies/{id}/assignments`: 당사 담당 이력 조회·변경
- `/api/network/tree`: 원청 기준 계보 조회

목록 API는 원청, 회사 구분, 담당자, 상태 및 검색어 필터를 지원한다. 계보 조회는 경로와 계산된 단계를 반환하며 순환 데이터가 존재할 경우 안전하게 탐색을 중단한다.

## 9. 오류 처리

- 권한 없음: `403 Forbidden`
- 존재하지 않는 회사·관계: `404 Not Found`
- 중복 관계 또는 동시 수정 충돌: `409 Conflict`
- 순환 관계 또는 잘못된 기간: `422 Unprocessable Entity`
- 필수 입력 누락과 형식 오류: `400 Bad Request`

화면에서는 기술 메시지 대신 `이미 연결된 관계입니다`, `순환 관계는 등록할 수 없습니다`, `다른 사용자가 먼저 수정했습니다`처럼 사용자가 조치할 수 있는 문구를 표시한다.

## 10. 단계별 구현

1. **UI 목업**
   - 승인된 화면 구조를 기존 목업에 추가
   - 가상 데이터로 계보 탐색, 탭 전환, 등록·수정 흐름 표현
   - 사용자 승인 후 다음 단계 진행
2. **Front-end**
   - 목 데이터와 확정된 API 계약으로 화면 구현
   - 사용자 승인 후 다음 단계 진행
3. **Back-end**
   - 서비스, 권한, 순환 검증, API 구현
   - 임시 저장소로 검증 후 사용자 승인
4. **Database**
   - PostgreSQL 테이블, 제약조건, 마이그레이션 및 기존 거래처 연결
   - 배포 전 사용자 승인

각 단계의 테스트는 실행 직전에 사용자에게 별도 승인을 받는다.

## 11. 검증 전략

### 11.1 UI 목업

- 영업망 메뉴와 화면 이동
- 계보 펼침·접기와 회사 선택
- 탭별 정보 가독성
- 잠재회사 등록·전환 흐름

### 11.2 Front-end

- 검색 및 필터 상태
- 여러 원청에 동일 회사 표시
- 담당자 및 관계 입력 검증
- 권한별 버튼 표시
- API 오류 메시지 처리

### 11.3 Back-end

- 팀원 본인 담당 회사 수정 허용
- 타 담당 회사 수정 거부
- 팀장 전체 수정 허용
- 중복·자기 연결·순환 관계 차단
- 담당자 변경 이력과 감사 로그
- 잠재회사의 거래처 전환 원자성

### 11.4 Database

- 회사와 거래처 1:1 고유 제약
- 현재 담당자 회사별 한 명 제약
- 외래키와 사용 중지 데이터 보존
- 낙관적 동시성과 마이그레이션 검증
- 기존 거래처의 영업망 회사 자동 생성

## 12. 비기능 요구사항

- 연락처는 인증된 사내 사용자만 조회한다.
- 감사 로그에는 비밀번호나 인증정보를 저장하지 않는다.
- 계보 조회는 데이터 증가에 대비해 원청과 관계 상태 조건으로 제한한다.
- 기존 백업 및 30일 보관 정책에 신규 테이블을 포함한다.
- 현재 Render 테스트 환경과 향후 Windows 사내망 배포에서 동일 기능을 제공한다.
