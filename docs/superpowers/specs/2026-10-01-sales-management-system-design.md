# 영업관리 시스템 설계 명세

- 작성일: 2026-10-01
- 회사명: 스위치코리아 (SWITCH KOREA)
- 대상: 스위치(전자부품) 제조업체 영업팀
- 사용자: 팀장 이재학, 팀원 박태원·최명철·이소연·이창선(총 5명)
- 배포 환경: Windows 기반 사내 서버, 사내망 전용 웹 시스템

## 1. 목적과 성공 기준

담당자별로 분산된 ERP 및 Excel 자료를 하나의 시스템에서 관리하여 다음 문제를 해결한다.

1. 담당자마다 다른 자료 형식과 수작업 취합
2. 분산된 ERP·Excel 자료로 인한 최신 매출 파악 지연
3. 거래처별 품목·단가와 변경 이력 추적의 어려움

1차 운영 버전의 성공 기준은 다음과 같다.

- 모든 팀원이 동일한 거래처·품목·출고 형식 사용
- Excel 일괄 등록과 건별 직접 입력 모두 지원
- 담당자별·거래처별·품목별 일간 및 월간 매출 확인
- 월 목표 대비 달성률 확인
- 거래처별 단가와 변경 이력 추적
- 팀장과 팀원의 권한 분리 및 주요 변경 감사 이력 보존

## 2. 전체 프로젝트 범위

전체 시스템은 다음 네 모듈로 구성한다.

1. 영업관리 프로그램
2. 영업망(네트워크 및 계보도)
3. B2B 견적 작성 및 고객문의 대응
4. 글로벌 B2B 타깃 기업 발굴 및 잠재고객 리서치 자동화

1차 구현 범위는 공통 기반과 영업관리 프로그램으로 제한한다. 나머지 모듈은 후속 프로젝트로 분리하되, 향후 동일한 거래처 식별자와 사용자 체계에 연결할 수 있도록 한다.

### 2.1 1차 포함 범위

- 로그인, 사용자 및 권한 관리
- 거래처 관리
- 품목과 거래처별 단가 관리
- 출고 및 매출 관리
- 월별 적용환율과 일별 공시환율 관리
- 담당자별 월 매출목표 관리
- 매출 대시보드
- Excel 가져오기
- 감사 이력과 백업

### 2.2 1차 제외 범위

- ERP 자동 또는 실시간 연동
- 원청·협력사 계보도와 거래처 담당자 관리
- 견적서 작성과 고객문의 처리
- 글로벌 잠재고객 자동 리서치
- 사외 인터넷을 통한 사용자 접속

ERP 연동 가능 여부가 확정되기 전까지 ERP에서 내려받은 Excel 파일을 사용한다. 향후 자동 연동은 Back-end의 별도 연결 모듈로 추가한다.

## 3. 아키텍처

5명 규모의 운영 효율과 후속 모듈 확장을 함께 고려하여 모듈형 단일 애플리케이션을 사용한다. 마이크로서비스는 도입하지 않는다.

```text
팀원 PC 웹브라우저
        ↓ 사내망
Windows 서버 / IIS
 ├─ React Front-end
 └─ ASP.NET Core Web API
       ├─ 인증·권한
       ├─ 기준정보
       ├─ 출고·매출
       ├─ 환율·목표
       ├─ Excel 처리
       └─ 환율 수집 작업
              ↓
          PostgreSQL
```

### 3.1 기술 구성

- UI 목업: 독립 실행형 HTML, CSS, JavaScript
- Front-end: React, TypeScript
- Back-end: ASP.NET Core Web API
- Database: PostgreSQL
- 웹 서버: IIS
- Excel 형식: `.xlsx`
- 일별 환율: 서버에서 외부 환율 제공처로 자동 조회

구현 시점에 지원되는 안정 버전을 선정하고, 개발·운영 버전을 동일하게 고정한다.

### 3.2 배포 원칙

- 사내 DNS가 있으면 `http://sales`와 같은 내부 주소를 사용한다.
- 방화벽에서 사내망 클라이언트만 접근하도록 제한한다.
- IIS가 Front-end 정적 파일과 Back-end API를 동일 출처로 제공한다.
- 애플리케이션과 데이터베이스는 Windows 시작 후 자동 실행한다.
- 외부 인터넷 연결은 서버의 일별 환율 수집에만 사용한다.

## 4. 사용자와 권한

### 4.1 팀장

- 전체 거래처, 품목, 단가, 출고 및 매출 조회
- 모든 업무 데이터 등록과 수정
- 거래처 담당자 배정 및 변경
- 사용자 생성, 초기 비밀번호 발급, 사용 중지
- 월별 적용환율 및 담당자별 목표 설정
- 감사 이력 조회
- 과거 매출의 명시적 재계산 수행

### 4.2 팀원

- 전체 거래처와 매출 현황 조회
- 본인 담당 거래처의 정보, 단가 및 출고 자료 등록과 수정
- 타 담당자의 업무 자료 수정 불가

Front-end의 버튼 표시 여부와 관계없이 Back-end가 모든 조회·수정 요청의 권한을 검사한다.

## 6. 핵심 업무 흐름

### 6.1 월 업무 시작

1. 팀장이 해당 월의 USD·CNY 적용환율을 지정한다.
2. 팀장이 담당자별 원화 매출목표를 입력한다.
3. 시스템은 설정 완료 여부를 표시한다.

### 6.2 출고 직접 입력

1. 담당자가 본인 담당 거래처를 선택한다.
2. 출고일과 품목을 기준으로 유효한 단가를 불러온다.
3. 수량을 입력하면 공급가액과 원화 환산금액을 계산한다.
4. 사용자가 확인한 뒤 저장한다.
5. 대시보드 집계에 반영한다.

### 6.3 Excel 출고 등록

1. 사용자가 `.xlsx` 파일을 업로드한다.
2. 시스템이 열과 필수값을 검증한다.
3. 신규, 중복, 변경 후보 및 오류를 구분하여 표시한다.
4. 사용자가 결과를 확인하고 반영을 요청한다.
5. 전체 데이터가 정상일 때 하나의 작업 단위로 저장한다.
6. 업로드 결과와 수행자를 기록한다.

### 6.4 대시보드 조회

1. 사용자가 기간과 필터를 선택한다.
2. Back-end가 권한 범위와 집계 조건을 확인한다.
3. 원통화와 원화 환산 결과, 목표 달성률을 반환한다.

## 8. 계산 및 이력 원칙

대시보드의 매출 기준은 부가세 제외 공급가액이다.

```text
공급가액 = 출고수량 × 출고 당시 적용단가
원화 환산매출 = 공급가액 × 출고 당시 월 지정환율
달성률 = 원화 환산매출 ÷ 월 목표 × 100
```

- KRW 환율은 1로 처리한다.
- USD와 CNY는 출고월의 팀장 지정환율을 사용한다.
- 일별 공시환율은 참고용이며 매출 계산에 사용하지 않는다.
- 출고 저장 시 단가, 지정환율, 공급가액 및 원화 환산금액을 함께 보존한다.
- 단가나 지정환율을 나중에 바꿔도 확정된 과거 출고는 자동 변경하지 않는다.
- 과거 자료 재계산은 팀장이 대상과 영향을 확인한 후 명시적으로 실행한다.
- 삭제 대신 취소 또는 사용 중지 상태를 사용한다.

출고번호가 있으면 거래처와 출고번호의 조합을 중복 판정의 우선 키로 사용한다. 출고번호가 없는 과거 자료는 출고일, 거래처, 품목, 수량의 조합으로 중복 후보를 찾아 사용자가 최종 판단한다.

## 9. 오류 처리

- Excel 자료는 검증 영역에서 확인한 뒤 실제 데이터에 반영한다.
- 치명적 오류가 있으면 해당 업로드 전체를 반영하지 않는다.
- 행별 오류 위치와 원인을 사용자가 수정할 수 있는 문구로 표시한다.
- 동시에 같은 자료를 수정한 경우 먼저 저장된 내용을 덮어쓰지 않고 최신 자료 재확인을 요구한다.
- 환율 수집 실패 시 마지막 성공 값, 갱신 시각 및 실패 상태를 표시한다.
- 환율 수집 실패가 지정환율 기반 매출 업무를 중단시키지 않도록 분리한다.
- 시스템 오류 로그에 비밀번호, 인증 쿠키 또는 원본 인증정보를 기록하지 않는다.

## 10. 보안과 운영

- 비밀번호는 복호화할 수 없는 안전한 해시로 저장한다.
- 최초 로그인 시 초기 비밀번호 변경을 요구한다.
- 연속 로그인 실패 시 계정을 임시 잠근다.
- 일정 시간 미사용 시 자동 로그아웃한다.
- 로그인과 주요 데이터 변경 이력을 보존한다.
- 데이터베이스를 매일 자동 백업하고 관리자가 수동 백업할 수 있게 한다.
- 백업 보관기간과 저장 위치는 Database 단계에서 서버 용량 및 회사 정책을 확인한 후 확정한다.
- 복원 절차는 운영 인수 문서에 포함한다.

## 11. 단계별 개발 및 승인 게이트

사용자 승인 없이 다음 단계로 넘어가지 않는다.

1. **UI 목업**
   - 가상 데이터로 전체 화면과 업무 흐름 작성
   - 사용자 검토와 승인
2. **Front-end**
   - 승인된 화면 구현
   - 임시 데이터와 확정된 API 계약 사용
   - 사용자 검토와 승인
3. **Back-end**
   - 로그인, 권한, 계산, Excel 처리 및 환율 수집 API 구현
   - 사용자 검토와 승인
4. **Database**
   - 실제 테이블, 제약조건, 인덱스, 감사 이력 및 백업 구축
   - Back-end와 연결 후 사용자 검토와 승인

Database 구현이 마지막 단계이더라도 데이터 개념 모델과 API 계약은 앞 단계에서 유지한다. Front-end와 Back-end는 각각 목 데이터와 임시 저장소를 사용하여 단계별 승인을 가능하게 한다.

## 12. 검증 전략

검증 항목은 사전에 정의하되, 실제 테스트는 매 단계마다 사용자에게 허가를 받은 뒤 실행한다.

- UI 목업: 메뉴 이동, 입력 흐름, 정보 가독성
- Front-end: 입력값 검증, 필터, 합계와 통화 표시
- Back-end: 로그인, 권한 우회 방지, 금액·환율 계산, Excel 오류 처리
- Database: 중복 방지, 관계 무결성, 감사 이력, 백업과 복원
- 통합: 팀장·팀원 권한 및 업로드부터 대시보드 반영까지의 흐름

## 13. 후속 모듈 연결 원칙

- 영업망 모듈은 거래처에 원청·협력사 관계와 거래처 담당자 이력을 연결한다.
- 견적·문의 모듈은 거래처, 품목, 단가 및 담당 사용자 정보를 재사용한다.
- 잠재고객 리서치 모듈은 검토 전 잠재고객을 별도로 보관하고, 승인된 기업만 정식 거래처로 전환한다.
- 후속 모듈은 각각 별도 설계, 계획, 구현 및 승인 과정을 거친다.

## 14. 미확정 운영 항목

다음 항목은 기능 범위의 미정 사항이 아니라, 해당 구현 단계에서 실제 사내 환경을 확인하여 결정할 운영 설정이다.

- 사내 서버의 정확한 Windows 버전과 하드웨어 용량
- 사내 DNS 이름과 TLS 인증서 사용 여부
- 일별 공시환율 제공처
- 표준 Excel 양식과 기존 파일의 열 이름
- 비밀번호 길이, 잠금 횟수 및 세션 만료시간의 회사 정책값
- 백업 저장 위치와 보관기간
