# 글로벌 B2B 잠재고객 리서치 자동화 설계 명세

- 작성일: 2026-10-07
- 회사명: 스위치코리아(SWITCH KOREA)
- 대상 시스템: 영업관리 시스템 4번 모듈
- 사용자: 팀장 이재학, 팀원 박태원·최명철·이소연·이창선
- 기반 시스템: React, ASP.NET Core, PostgreSQL 기반 모듈형 단일 애플리케이션

## 1. 목적과 성공 기준

한국·유럽·미국·중국·인도·베트남 및 기타 동남아 지역에서 스위치 제품의 적용 가능성이 있는 기업을 반복적으로 발굴하고, 담당자의 검토를 거친 기업만 기존 영업망의 잠재기업으로 전환한다.

MVP의 성공 기준은 다음과 같다.

- 수동 실행, 매주 예약 실행, Excel 업로드의 세 경로로 후보를 생성한다.
- 모든 후보에 규칙 점수, AI 요약, 출처 URL 및 조사일을 표시한다.
- 기존 후보, 영업망 기업 및 거래처와 중복 여부를 확인한다.
- 담당자가 검토하고 팀장이 승인한 기업만 영업망 잠재기업으로 전환한다.
- 팀장과 팀원의 권한, 감사 이력, API 사용량 및 비용 한도를 적용한다.
- 외부 검색·AI 서비스 장애가 기존 영업관리 업무에 영향을 주지 않는다.

## 2. 범위

### 2.1 포함 범위

- 지역·업종·기업규모·키워드·원청 및 공급망 조건으로 구성된 타깃 프로필
- 공개 웹 검색을 통한 후보 발굴
- Excel 후보 목록 업로드 및 공개 정보 보강
- 홈페이지, 국가, 업종, 기업규모, 제품 및 적용 분야 정보 수집
- 규칙 기반 점수와 AI 요약·추천 생성
- 근거 URL, 조사일, 신뢰도 및 요약 보관
- 도메인·회사명·국가 기준의 중복 판정
- 후보 검토, 담당자 배정, 보류, 제외 및 승인
- 승인된 후보의 기존 `NetworkCompany` 잠재기업 전환
- 수동 실행과 매주 예약 실행
- 실행 이력, 오류, 사용량, 비용 한도 및 감사 이력

### 2.2 제외 범위

- 잠재고객에 대한 자동 이메일 또는 메시지 발송
- 로그인, 유료 구독 또는 접근 제한 페이지 수집
- 개인 연락처의 대량 수집
- AI의 무승인 거래처 생성
- 유료 기업정보 데이터 구매 및 계약
- B2B 견적·문의 대응 모듈

## 3. 설계 원칙

1. 기존 모듈형 단일 애플리케이션에 독립적인 `Prospect Research` 모듈을 추가한다.
2. 검색과 AI 공급자는 어댑터로 분리하여 교체할 수 있게 한다.
3. AI는 추천과 요약만 제공하며 업무 상태와 거래처 전환을 직접 결정하지 않는다.
4. 출처와 조사일이 없는 AI 결과는 승인할 수 없다.
5. 공개된 기업·업무 정보만 수집하고 기존 고객 개인정보와 내부 매출자료를 외부 AI에 전송하지 않는다.
6. 검색, 보강, 평가 및 전환 단계를 분리하여 부분 실패와 재처리를 허용한다.
7. 동일 입력을 재실행해도 같은 후보가 중복 생성되지 않도록 멱등성을 보장한다.

## 4. 아키텍처

```text
수동 실행 / 매주 예약 실행 / Excel 업로드
                 |
                 v
          리서치 작업 대기열
                 |
                 v
 검색 공급자 -> 후보 정규화 -> 중복 확인
                 |
                 v
 기업정보 보강 -> 규칙 점수 -> AI 요약
                 |
                 v
          잠재고객 검토함
                 |
           담당자 및 팀장 승인
                 |
                 v
     기존 영업망의 잠재기업으로 전환
```

### 4.1 주요 구성요소

- `TargetProfileService`: 검색 대상과 제외 조건 관리
- `ResearchRunService`: 수동·예약·Excel 실행 생성 및 상태 관리
- `SearchProvider`: 외부 검색 공급자 추상화
- `AiAssessmentProvider`: 요약과 적합성 추천 공급자 추상화
- `CandidateNormalizer`: 회사명, 국가, 도메인 및 업종 정규화
- `DuplicateDetectionService`: 후보·영업망·거래처 중복 판정
- `ProspectScoringService`: 규칙 점수와 규칙 버전 관리
- `ProspectReviewService`: 검토 상태, 담당자, 메모 및 승인 관리
- `ProspectConversionService`: 승인 후보를 `NetworkCompany`로 전환
- `ResearchWorker`: 대기열 처리, 재시도 및 예약 실행
- `UsageBudgetService`: 호출량, 예상 비용 및 한도 관리

각 서비스는 명확한 입력·출력 계약을 가지며 검색·AI 공급자 장애가 검토와 기존 영업 업무를 중단시키지 않도록 분리한다.

### 5.2 타깃 프로필

### 5.4 후보 상세

- 기업 개요, 홈페이지, 국가, 업종, 규모

- 총점과 항목별 점수
- AI 요약, 추천 사유 및 위험요소
- 출처 링크, 조사일, 신뢰도
- 담당자, 메모 및 상태 변경 이력
- 잠재기업 전환 및 중복 병합 작업

### 5.5 실행 관리

- 즉시 조사 실행

- 공개 정보 자동 보강 결과 미리보기
- 사용자가 확인한 정상 행만 후보 검토함에 반영

### 5.7 제외 목록

## 6. 업무 흐름과 상태

```text
수집됨 -> 정보 보강 중 -> 검토 대기
                         |- 담당자 배정
                         |- 중복 의심
                         |- 보류
                         |- 제외
                         `- 승인 -> 영업망 잠재기업 -> 정식 거래처
```

후보 상태는 `Collected`, `Enriching`, `ReviewPending`, `DuplicateSuspected`, `OnHold`, `Excluded`, `Approved`, `Converted`로 관리한다.

- 정보 보강 실패 후보는 원본 후보를 유지하고 오류 상태와 재처리 가능 여부를 표시한다.
- `Approved` 전환은 팀장만 수행한다.
- `Converted` 후보는 생성된 `NetworkCompany` 식별자를 보존한다.
- 정식 거래처 전환은 기존 영업망 모듈의 팀장 승인 흐름을 재사용한다.

- 영업망 잠재기업 전환

### 7.2 팀원

## 8. 데이터 개념 모델

| 엔터티 | 핵심 정보 |
|---|---|
| `ResearchTargetProfile` | 이름, 지역, 업종, 포함·제외 조건, 실행 한도, 활성 상태, 버전 |
| `ResearchRun` | 실행 방식, 프로필, 시작·종료, 상태, 처리 건수, 사용량, 오류 요약 |
| `ProspectCandidate` | 회사명, 영문명, 국가, 도메인, 홈페이지, 업종, 규모, 제품, 적용 분야, 담당자, 상태 |
| `ResearchEvidence` | 후보, 출처 URL, 제목, 확인일, 내용 요약, 신뢰도, 원본 해시 |
| `ProspectScore` | 후보, 총점, 항목별 점수, 규칙 버전, 평가일 |
| `AiAssessment` | 후보, 요약, 추천 사유, 위험요소, 모델, 생성일 |
| `DuplicateMatch` | 후보, 비교 대상 유형·식별자, 유사도, 근거, 판정 상태 |
| `ProspectActivity` | 후보, 수행자, 작업, 메모, 변경 전·후, 수행일 |
| `ProspectConversion` | 후보, `NetworkCompany`, 승인자, 전환일 |
| `ResearchExclusion` | 대상 유형, 값, 사유, 등록자, 유효 상태 |

실제 키, 인덱스 및 제약조건은 Database 단계에서 확정한다. API 식별자는 UUID를 사용하고 모든 수정 가능한 엔터티에 낙관적 동시성 버전을 둔다.

## 9. 점수 산정

100점 만점의 기본 규칙은 다음과 같다.

| 평가 항목 | 배점 |
|---|---:|
| 스위치 제품 적용 가능성 | 30 |
| 타깃 업종 적합성 | 20 |
| 원청·협력사 공급망 연관성 | 20 |
| 우선 지역 적합성 | 10 |
| 기업규모·구매 잠재력 | 10 |
| 정보 신뢰도와 출처 충실도 | 10 |

- 70점 이상: 우선 검토
- 50~69점: 일반 검토
- 49점 이하: 낮은 우선순위
- 중복 의심 후보: 점수와 무관하게 중복 검토함으로 이동

규칙 변경 시 새 버전을 생성하며 기존 평가 결과와 사용 규칙 버전을 보존한다. AI 의견은 점수를 덮어쓰지 않는다.

## 10. 중복 판정

중복 판정은 확정 규칙과 유사도 규칙을 구분한다.

1. 정규화된 루트 도메인이 동일하면 강한 중복 후보로 판정한다.
2. 국가와 정규화된 회사명이 동일하면 강한 중복 후보로 판정한다.
3. 회사명 유사도, 홈페이지, 주소 및 대표전화 일부가 일치하면 검토 대상으로 표시한다.
4. 기존 거래처, `NetworkCompany`, 다른 잠재후보를 모두 비교한다.
5. 자동 병합하지 않고 담당자 또는 팀장이 신규, 중복, 병합을 결정한다.

## 11. 외부 API와 비용 통제

- 검색과 AI API 키는 서버의 비밀 환경변수로 관리한다.
- 동일 도메인과 검색조건은 일정 기간 캐시한다.
- 프로필별 실행당 검색 건수와 AI 분석 건수를 제한한다.
- 월 한도 70%와 90%에서 팀장 화면에 경고한다.
- 월 한도 100%에서는 예약 실행만 중지하고 수동 실행은 팀장 확인 후 허용한다.
- 실행 이력에는 공급자, 호출 수, 토큰 또는 과금 단위, 예상 비용을 기록한다.
- 공급자 응답 전문은 필요한 최소 기간만 보관하고 업무 데이터에는 정규화된 결과와 근거만 저장한다.

## 12. 오류 처리와 재처리

- 검색·AI의 일시적 오류는 지수 백오프로 제한 재시도한다.
- 반복 실패 항목은 재처리 대기열로 이동한다.
- 실행 일부가 실패해도 정상 후보는 검토함에 반영한다.
- 각 후보는 `ResearchRun`과 공급자 결과 식별자를 보존하여 재실행 중복을 방지한다.
- Excel은 검증 결과를 먼저 표시하고 사용자가 확정한 행만 반영한다.
- 외부 API 장애 시 기존 후보 조회·검토·전환과 다른 영업관리 기능은 계속 동작한다.
- 동시 수정 충돌 시 먼저 저장된 데이터를 덮어쓰지 않고 최신 상태 재확인을 요구한다.

## 13. 보안과 준법

- 공개된 기업 및 업무 정보만 수집한다.
- 로그인 우회, CAPTCHA 우회, 유료 페이지 우회 또는 사이트 접근통제 우회를 하지 않는다.
- 사이트 이용조건과 수집 허용 범위를 위반하는 직접 크롤링을 하지 않는다.
- 기존 고객 개인정보, 내부 매출, 단가 및 인증정보를 외부 AI에 전송하지 않는다.
- 비밀번호, 인증 쿠키, API 키 및 공급자 원문 응답의 민감정보를 로그에 기록하지 않는다.
- 후보 승인, 제외, 담당자 변경, 중복 판정 및 전환을 감사 이력으로 남긴다.

## 14. 단계별 구현과 승인 게이트

### 14.1 UI 목업

- 독립 실행형 HTML, CSS, JavaScript와 가상 데이터 사용
- 전체 메뉴, 필터, 후보 검토, 상세, 중복 비교, 실행 및 Excel 흐름 구현
- 사용자 검토 후 Front-end 단계 진행

### 14.2 Front-end

- Mock API와 확정된 계약 사용
- 필터, 정렬, 상태 변경, 담당자 배정, 중복 판정 및 승인 흐름 구현
- 사용자 검토 후 Back-end 단계 진행

### 14.3 Back-end

- ASP.NET Core 서비스와 API 구현
- 인메모리 저장소로 업무 규칙과 권한 검증
- 작업 대기열, 예약 실행, 공급자 인터페이스, 점수, 중복 및 전환 구현
- 사용자 검토 후 Database 단계 진행

### 14.4 Database

- PostgreSQL 테이블, 관계, 제약조건, 인덱스 및 마이그레이션 구현
- 실제 검색·AI 공급자와 Render 환경변수 연결
- 운영 스케줄, 사용량 한도, 감사 및 백업 범위 연결
- 사용자 검토 후 배포

## 15. 검증 전략

검증 항목은 사전에 정의하되 실제 테스트는 각 단계에서 사용자 허락을 받은 뒤 실행한다.

### 15.1 UI 목업

- 메뉴 이동과 화면 가독성
- 수동 실행부터 후보 승인까지의 업무 흐름
- 중복 비교와 출처 확인의 이해 가능성

### 15.2 Front-end

- 필터, 정렬, 페이지 이동 및 입력값 검증
- 상태별 버튼과 팀장·팀원 권한 표시
- 외부 API 오류, 빈 결과 및 부분 성공 표시
- API 계약과 Mock API 일치

### 15.3 Back-end

- 점수 계산과 규칙 버전 보존
- 중복 판정과 멱등 처리
- 팀장·팀원 권한 우회 방지
- 예약·수동·Excel 실행과 부분 실패
- 후보 승인과 `NetworkCompany` 전환
- 사용량 한도와 외부 공급자 장애 격리

### 15.4 Database

- 도메인·회사명 정규화 인덱스와 중복 방지
- 관계 무결성, 동시성 및 감사 이력
- 작업 재시작과 재처리 후 멱등성
- 마이그레이션 적용과 롤백 가능성
- 백업 대상 포함 여부와 복원 확인

## 16. 배포와 운영

- 개발과 임시 검증은 현재 Render 테스트 환경을 사용한다.
- 외부 API 키는 Render 비밀 환경변수로 설정하며 소스 저장소에 커밋하지 않는다.
- 예약 실행 시각은 `Asia/Seoul` 기준으로 저장하고 화면에 표시한다.
- 무료 또는 저비용 테스트 환경에서는 실행 한도를 보수적으로 설정한다.
- 사내 Windows 서버 이전 시 동일한 공급자 설정, 예약 작업 및 PostgreSQL 데이터를 이전한다.

## 17. 완료 정의

다음 조건을 모두 충족하면 4번 모듈 MVP를 완료한 것으로 판단한다.

1. 세 가지 입력 경로에서 후보를 생성할 수 있다.
2. 후보마다 점수, AI 요약, 근거 URL, 조사일 및 담당자를 확인할 수 있다.
3. 중복 후보가 자동 병합되지 않고 검토 대상으로 분리된다.
4. 팀원은 본인 담당 후보만 변경하며 팀장만 최종 승인한다.
5. 승인 후보가 감사 이력과 함께 기존 영업망 잠재기업으로 전환된다.
6. 외부 API 장애와 비용 한도 초과가 기존 영업관리 기능을 중단시키지 않는다.
7. 각 단계에서 승인된 화면·계약·업무 규칙과 구현이 일치한다.
