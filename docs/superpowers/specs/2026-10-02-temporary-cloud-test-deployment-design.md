# SWITCH KOREA 임시 클라우드 테스트 배포 설계

**작성일:** 2026-10-02  
**대상:** SWITCH KOREA 영업관리 시스템  
**목적:** 사내 PC 설치 전에 5명의 담당자가 인터넷을 통해 로그인하고 핵심 업무 흐름을 검증한다.

## 1. 범위와 성공 기준

임시 환경은 제품 검증용이며 운영 환경이 아니다. 팀장과 팀원이 각자 계정으로 로그인하고, 샘플 거래처·품목·출고 데이터를 등록·조회하며, 역할별 접근 권한과 대시보드 집계를 확인할 수 있어야 한다.

성공 기준은 다음과 같다.

- 5개 초기 계정이 서로 다른 임시 비밀번호로 생성된다.
- 사용자는 최초 로그인 후 비밀번호를 변경해야 한다.
- 팀원은 본인 담당 데이터를 관리하고, 팀장은 전체 데이터를 조회·관리한다.
- KRW, USD, CNY 판매 현황과 전체 매출 대비 통화별 비중이 표시된다.
- 제품과 상품 구분을 포함한 품목 등록이 동작한다.
- 거래처, 품목, 출고 데이터의 등록·수정·조회 흐름이 HTTPS에서 동작한다.
- 테스트 종료 후 임시 애플리케이션과 데이터베이스를 삭제할 수 있다.

## 2. 선택한 배포 방식

비공개 GitHub 저장소와 Render 무료 환경을 사용한다.

- GitHub private repository: 테스트 배포용 소스 저장
- Render Web Service: Docker 이미지로 .NET API 실행 및 빌드된 React 정적 파일 제공
- Render PostgreSQL: 테스트 데이터 저장
- Render 제공 `onrender.com` 주소와 자동 HTTPS 사용

사용자는 GitHub와 Render 계정을 직접 만들고 인증한다. 인증 완료 후 저장소 생성, 코드 업로드, 서비스 구성과 검증은 구현 절차에 포함한다.

Render 무료 Web Service는 유휴 상태에서 중지될 수 있어 첫 접속이 느릴 수 있다. 무료 PostgreSQL은 생성 후 30일에 만료되므로 테스트 기간은 최대 30일로 제한한다.

## 3. 애플리케이션 구조

단일 컨테이너가 프런트엔드와 백엔드를 함께 제공한다.

1. Docker 다단계 빌드에서 pnpm으로 React 프런트엔드를 빌드한다.
2. .NET SDK로 API와 초기 계정 생성 도구를 게시한다.
3. 프런트엔드 산출물을 API의 정적 파일 디렉터리에 복사한다.
4. 컨테이너 시작 시 데이터베이스 연결을 확인하고 EF Core 마이그레이션을 적용한다.
5. 초기 계정은 없는 경우에만 생성하여 재배포 시 비밀번호가 바뀌지 않게 한다.
6. API가 Render의 `PORT`에서 수신하고 동일 출처로 UI와 API를 제공한다.

이 구조는 별도 프런트엔드 서비스와 CORS 구성을 피하고 임시 환경의 운영 단위를 하나로 줄인다.

## 5. 데이터와 보안

- 테스트에는 가상의 회사명, 품목, 단가와 출고 데이터만 사용한다.
- 실제 고객 연락처, 단가, 계약, 견적 및 영업기회 정보는 입력하지 않는다.
- 데이터베이스 연결 문자열과 데이터 보호 키는 Render secret 환경변수로 관리한다.
- 애플리케이션은 Production 모드에서 PostgreSQL 연결 없이는 시작하지 않는다.
- HTTPS는 Render가 종단 처리하고 HTTP 요청은 HTTPS로 전환한다.
- 오류 응답과 로그에는 비밀번호, 연결 문자열 또는 토큰을 노출하지 않는다.
- 무료 환경의 자동 백업을 운영 백업으로 간주하지 않는다. 테스트 데이터는 삭제 가능 데이터로 취급한다.

## 6. 배포와 데이터 흐름

1. 로컬 검증을 통과한 커밋만 비공개 저장소의 테스트 브랜치에 업로드한다.
2. Render Blueprint가 Web Service와 PostgreSQL을 생성하고 비밀값을 주입한다.
3. 서비스 시작 과정에서 마이그레이션과 초기 계정 생성이 멱등적으로 수행된다.
4. 담당자는 Render HTTPS 주소에서 로그인하고 샘플 데이터를 입력한다.
5. 발견된 문제는 로컬에서 수정·검증한 뒤 테스트 브랜치 재배포로 확인한다.
6. 테스트 승인 버전만 현재 PC 사내망 설치 후보로 확정한다.

## 7. 오류 처리와 운영 제한

- DB 연결 실패 시 readiness 상태를 실패로 반환하고 서비스 시작 오류를 로그에 남긴다.
- 마이그레이션 또는 계정 생성 실패 시 컨테이너는 정상 상태로 표시되지 않는다.
- 무료 서비스가 유휴 중지된 경우 첫 요청은 준비될 때까지 기다린 후 재시도한다.
- 비밀번호 분실은 팀장 관리 기능 또는 계정 초기화 절차로 처리한다.
- 테스트 중 민감정보가 입력된 경우 즉시 서비스를 중지하고 DB를 삭제한 뒤 비밀값을 교체한다.

## 8. 검증 계획

배포 전에는 다음 자동검사를 수행한다.

- 프런트엔드 단위·통합 테스트 및 production build
- 백엔드 단위·통합 테스트
- PostgreSQL 마이그레이션과 초기 계정 생성의 멱등성 검사
- Docker 이미지 빌드 및 비밀정보 포함 여부 검사
- 컨테이너 기반 로그인, 권한, CRUD, 대시보드 집계 smoke test

배포 후에는 HTTPS 주소에서 다음을 확인한다.

- readiness 및 로그인 성공
- 최초 비밀번호 변경
- 팀원별 데이터 격리와 팀장 전체 조회
- 거래처·품목·출고 등록
- 제품/상품 구분
- KRW, USD, CNY 판매액과 통화별 비중
- 재배포 후 계정과 테스트 데이터 유지

## 9. 종료와 사내 설치 전환

테스트 종료 시 필요한 샘플 결과만 익명화해 기록하고 Render Web Service와 PostgreSQL을 삭제한다. 테스트 DB를 운영 DB로 복사하지 않는다. 승인된 소스 버전을 기준으로 현재 PC의 IIS, PostgreSQL, 사내 HTTPS 구조에 새 운영 DB를 설치한다.

## 10. 제외 범위

- 실제 영업 데이터의 클라우드 이전
- 운영용 고가용성, 장기 백업 및 재해 복구
- 사용자별 이메일 발송 또는 비밀번호 메일 전송
- 사용자 정의 도메인 구매
- 테스트 환경을 그대로 정식 운영 환경으로 전환
